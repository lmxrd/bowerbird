# M6e design proposal — end-to-end-encrypted folders

Status: **accepted 2026-11-08** (§7), **built** (§8). The last
step of M6 ([M6_OUTLINE.md](M6_OUTLINE.md)): folders whose names and
contents the server cannot read.

Decided already (2026-11-08):
- **A passphrase and a recovery key** protect each user's key; the login
  (password, passkey, single sign-on) is never the key.
- **Platform-native primitives**: X25519, HKDF-SHA256, AES-256-GCM and
  PBKDF2-HMAC-SHA256, through WebCrypto (web), CryptoKit and CommonCrypto
  (iOS), Tink and the JDK (Android) and RustCrypto (desktop, server
  tests), with a small specification of our own (§3); **file and folder
  names are encrypted too**.
- **All four clients**: web, desktop, iOS and Android.

## 1. What the user sees

- **Settings → Encryption**: "Set up encryption" asks for an encryption
  passphrase (not the login password) and shows a **recovery key** once,
  to write down or save. Later: unlock on a new device, change the
  passphrase, use the recovery key when the passphrase is forgotten.
- **New folder → "Encrypt this folder"**: an encrypted folder at the top
  of the user's files or inside one of their own folders (not inside a
  shared folder they don't own, not in the drop box).
- An encrypted folder shows a **lock**. Locked on a device (passphrase not
  given there yet), it shows "Unlock to see what's inside"; unlocked, it
  works as any folder: browse, open, upload, rename, move, delete, the
  trash and versions (as unreadable bytes the client decrypts).
- **Sharing with people** (M6b) works: the folder's key is wrapped for the
  recipient's public key by the sharer's device. Someone who has not set
  up encryption appears as "waiting for them to set up encryption", and
  gets access when they do and the owner's device next runs.
- **Not for encrypted folders**: AI placement (the drop box never proposes
  them and never reads them), the server's search of their names and
  text, previews generated by the server, public links, WebDAV (they are
  hidden there: a WebDAV client cannot decrypt).

## 2. Keys

- Each user has an **identity key pair** (X25519). Its private key is
  stored on the server twice, encrypted: once under a key derived from the
  **passphrase** (PBKDF2-HMAC-SHA256, 600,000 iterations, random salt) and
  once under the **recovery key** (256 random bits, shown as 13 groups of
  4 base32 characters). The public key is stored in plain.
- Each encrypted folder has a random **folder key** (256 bits), stored
  **wrapped** for each member: an ephemeral X25519 key agreement with the
  member's public key, HKDF, AES-256-GCM (the folder's id bound as
  associated data).
- A device keeps the **unlocked private key** in the platform's secure
  store (Keychain, Android Keystore-encrypted storage, the desktop's
  credential store); the web keeps it as a non-extractable `CryptoKey` for
  the session only.
- **Removing someone** from an encrypted folder makes a new folder key for
  everything written after; what they could read before stays readable to
  a copy they made (as with any sharing).

## 3. The format (docs/E2E_SPEC.md, with test vectors)

- **Contents**: a header (format version, a random 32-byte file nonce),
  then the contents in 64 KiB segments, each sealed with AES-256-GCM under
  a file key = HKDF(folder key, file nonce), with the segment number and a
  last-segment flag in the nonce, so segments cannot be reordered, cut or
  extended.
- **Names**: AES-256-GCM under a name key = HKDF(folder key, "name"), with
  the parent folder's id as associated data (a name moved elsewhere by the
  server fails to decrypt), base64url; the client checks for duplicate
  names (the server cannot).
- **Test vectors** made by the Rust reference implementation are checked by
  each client's tests, so the four implementations agree.

## 4. The server

- Nodes get an `encrypted` flag (a folder and everything in it), and the
  server keeps: users' public keys and encrypted private keys, the
  wrapped folder keys per member, and the opaque names and contents.
- It refuses what it cannot do correctly for them (extraction, AI, search
  text, server previews, links, WebDAV), and checks only what it can:
  sizes, the storage limit, permissions, versions.
- Backups contain them as they are: still encrypted.

## 5. Pages (mockups)

1. Settings → Encryption: set up (passphrase twice, then the recovery key
   with Copy/Download and "I have saved it"), and when set up: Unlock on
   this device, Change passphrase, Use the recovery key.
2. The New folder dialog's "Encrypt this folder" switch; a locked folder's
   empty state.
3. The Share dialog for an encrypted folder: people and groups only (no
   links), "waiting to set up encryption" on someone without keys.

## 6. Order

1. The spec and the Rust reference with test vectors (packages/e2e-crypto
   or in packages/sync), the server's tables and rules.
2. Web, then desktop, iOS and Android, each with the vectors.

## 7. Decided (2026-11-08)

1. **The design** (§1–§4) as proposed.
2. **The pages** as mocked up.
3. **A command-line fallback** to decrypt by hand, documented: a small
   `organizer-decrypt` tool (from the Rust reference implementation) that
   takes the passphrase or the recovery key and decrypts an encrypted
   folder, either downloaded from a running server (with an API key) or
   straight from a restored backup (its database and files), so a user is
   never dependent on the apps to read their own files. docs/E2E_SPEC.md
   and the README say how, step by step.

## 8. Built (2026-11-08)

As designed, with these choices made while building:

- **Format** (docs/E2E_SPEC.md): versioned (first byte 1); a folder's keys
  have **generations**, the generation in each name and file header; the
  ephemeral-X25519 wrapping binds the folder's id and the generation; the
  recovery key is RFC 4648 base32, strictly read; PBKDF2's count is stored
  (600,000 new, at least 100,000 read). The encrypted folder's **own name
  stays plain** (a locked device shows it); everything under it is sealed.
- **Crate** `packages/e2e-crypto` on the RustCrypto crates already in the
  tree (x25519 through curve25519-dalek's Montgomery points, aes-gcm 0.11,
  hkdf 0.13, pbkdf2 0.13, sha2 0.11), `vectors.json` from fixed inputs,
  `organizer-decrypt` (no argument crate: a few flags parsed by hand).
- **Server**: migration 0023, `/api/encryption` (keys, a folder's keys and
  members, keys posted for members and new generations, `/pending` for a
  device to see to). A new folder has no key until its owner's device
  posts generation 1; any member's device wraps for members waiting and
  makes a new generation after someone lost access. Trash restores keep
  the ids of encrypted nodes. A removed user's keys go with them (no new
  generation is asked for: they can no longer reach the server).
- **On-demand folders** (M5b): an encrypted folder is never on demand.
  A placeholder's bytes come straight from the server when the system asks
  (Windows' Cloud Files fetch, macOS' File Provider extension), so they
  would be sealed; the engine refuses an encrypted folder (or one inside
  one) on demand, the desktop's Add a folder offers only Sync for it, and
  the encrypted folders inside an on-demand folder are left out of it (the
  engine hides them as it does a locked one; the macOS extension leaves
  them out of its listings and working set). They sync in full.
- **Not done:** keys are not compared out of band (the server is trusted to
  hand out the right public keys, docs/E2E_SPEC.md §1); search and the
  Shared-with-me page show nothing decrypted; the iOS and Android apps do
  not make encrypted folders (the web does); moving inside an encrypted
  folder is on the web, desktop and iOS.
